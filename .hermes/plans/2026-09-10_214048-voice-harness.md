# Voice Harness — Rust Voice Assistant Bridge (Implementation Plan)

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** A Rust daemon on the voicebox box that sits between clients (ESP32-class smart speakers, desktop apps) and the existing servers: it accepts streamed PCM16 mic audio or pre-transcribed text, runs an agentic pipeline (system prompt + MCP-style plugin tools → LLM), and returns transcript + streamed sentence-chunked TTS audio.

**Architecture:** Single tokio/axum server exposing `POST /v1/turn` (request/response, text or audio) and `WS /v1/realtime` (streaming audio in, streamed audio chunks out). Server-side silence/VAD detection segments client audio into utterances; each utterance → STT → prompt build → streaming LLM call → sentence chunker → TTS per chunk → ordered audio frames back to the client. Tool calling is plugin-based: a `Plugin` trait supplies OpenAI-style tool specs and handlers; built-ins ship (time, http_fetch), dynamic loading is deferred.

**Tech Stack:** Rust, tokio, axum (HTTP+WS), reqwest + eventsource-stream (SSE), serde/serde_json, webrtc-vad crate (endpointing), thiserror, tracing, wiremock (mock upstreams in tests), `config` crate (env/file config).

## Non-goals (v1)

- No wake-word, no on-device VAD requirement, no client push-to-talk contract (server VAD decides turn end; a client `speech.end` message is honored if sent).
- No barge-in/interruption (stretch Task 16), no multi-room/device identity beyond an optional `device_id` string.
- No dynamic plugin hot-loading (`.so`/WASM) — plugins compile in behind a trait; a registry + manifest design keeps the door open.
- No per-user memory/history beyond a per-session in-RAM conversation buffer (configurable max turns).

## Wire protocol — WS `/v1/realtime`

Client → server, JSON text frames (one per message):

```json
{"type":"session.start","device_id":"esp32-kitchen","sample_rate":16000,"encoding":"pcm16"}
{"type":"audio.data","pcm":"<base64 of arbitrary-length PCM16 chunk>"}   // 20–100ms chunks recommended
{"type":"speech.end"}                       // optional explicit end-of-utterance (client VAD/PTT)
{"type":"session.stop"}                     // optional; server also times idle sessions out
```

Server → client:

```json
{"type":"state","state":"listening|speech|thinking|speaking"}
{"type":"transcript","text":"..."}                        // finalized user utterance
{"type":"response.text.delta","text":"..."}               // raw LLM text deltas (for display)
{"type":"response.text","text":"..."}                     // full final text at turn end
{"type":"audio.chunk","pcm":"<base64 PCM16 mono>","seq":3}  // TTS output in playback order
{"type":"turn.completed"}
{"type":"error","code":"...","message":"..."}
```

Audio contract: **16 kHz, mono, PCM16 little-endian everywhere client↔harness.** Harness resamples only if it must (out of scope v1 — clients send 16k). TTS output is converted to 16k mono PCM16 before sending (resample in Task 8).

Turn lifecycle (server VAD): pre-speech ring buffer (500 ms) → VAD speech → accumulate → 700 ms silence → finalize → pipeline → `state: speaking` while audio chunks stream. Hard caps: min utterance 300 ms (discard blips), max 30 s (finalize anyway).

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "type", rename_all = "snake_case")]
pub enum ClientMsg {
    SessionStart { device_id: Option<String>, #[serde(default = "default_rate")] sample_rate: u32 },
    AudioData { pcm: String },          // base64
    SpeechEnd,
    SessionStop,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "type", rename_all = "snake_case")]
pub enum ServerMsg {
    State { state: SessionState },
    Transcript { text: String },
    ResponseTextDelta { text: String },
    ResponseText { text: String },
    AudioChunk { pcm: String, seq: u32 },
    TurnCompleted,
    Error { code: String, message: String },
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum SessionState { Listening, Speech, Thinking, Speaking }
```

Plugin trait (harness-plugins `lib.rs`):

```rust
#[async_trait::async_trait]
pub trait Plugin: Send + Sync {
    fn manifest(&self) -> &PluginManifest;                    // name, version, description
    fn tool_specs(&self) -> Vec<serde_json::Value>;           // OpenAI tool schema (type/function)
    async fn call(&self, name: &str, arguments: serde_json::Value) -> Result<serde_json::Value, String>;
}
```

Built-ins: `time` (current time/date/timezone — no network), `http_fetch` (GET allowlist from config `plugins.http_fetch.allowed_hosts`, size-capped, returns text). Registry resolves `(plugin, tool)` by function name; unknown → tool error message back to LLM (it can recover), never a 500.

## Risks / tradeoffs / open questions

- **Upstream API exactness** — nemo-speech is custom software; its "OpenAI-compatible" surface and `/v1/realtime` framing are assumed, not verified (auth is confirmed 401-protected). Mitigation: providers are thin traits; Task 14 probes and one config path fixes drift. If the realtime protocol is WebSocket-with-JSON similar to OpenAI, Task 16 is small; if it's something else, batch STT path already covers function.
- **Open WebUI chat path** — `/api/chat/completions` vs `/v1/chat/completions` (Task 5 note resolves it empirically). Also confirm the key it wants is the Open WebUI API token, not an upstream provider key.
- **Server-side VAD vs ESP32 reality** — 700 ms silence tail adds turn latency; make `silence_ms` per-session configurable via `session.start` extension later. Webrtc-VAD aggressiveness 2 chosen as start; tune with real recordings.
- **Auth model** — single shared token list is v1-fine for LAN/Tailscale; per-device keys + rate limits deferred.
- **TTS format** — magpie output format/sample rate unverified; Task 7's normalization (WAV parse + resample to 16 k) absorbs the common cases; if magpie only emits non-PCM (e.g. opus), add decode (symphonia) — flagged, not planned.
- **No barge-in in v1** — speakers will play responses to completion; acceptable for a first cut, cancel-on-`session.start` gives an escape hatch.
